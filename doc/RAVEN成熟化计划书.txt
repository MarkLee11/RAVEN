===============================================================================
RAVEN 成熟化计划书（V1）
===============================================================================
编制时间：2026-09-20
目标：将当前 RAVEN 从“可运行的项目”升级为“可持续迭代、可观测、可测试、可发布”的成熟应用。
适用范围：产品、前端、后端（Supabase）、数据、测试、CI/CD、安全、运维、增长。

-------------------------------------------------------------------------------
0. 先看结论（TL;DR）
-------------------------------------------------------------------------------
当前项目已经具备：
1) 清晰的 React + TypeScript + Supabase 技术栈
2) 核心业务流（浏览、详情、评论、收藏、用户登录）基本可用
3) 已有部署配置（Netlify/Vercel）和较完整的 README

但距离“成熟 app”仍有关键缺口：
1) 自动化测试几乎为空（无单测、无 E2E）
2) 无 CI 工作流（无 PR 质量门禁）
3) 认证、鉴权与路由保护仍有分散逻辑风险
4) 可观测性不足（日志、错误追踪、性能指标未体系化）
5) 数据治理薄弱（迁移命名、seed、环境隔离、回滚策略未固化）
6) 发布流程不标准（版本、变更记录、灰度/回滚机制不完整）

成熟化建议总周期：8~12 周（单人可执行，2~3 人更稳）

-------------------------------------------------------------------------------
1. 项目现状盘点（基于代码与目录）
-------------------------------------------------------------------------------
1.1 技术与结构
- 前端：React 18 + TypeScript + Vite + Tailwind + Framer Motion
- 数据层：Supabase（Auth + Postgres + RLS）
- 核心路由：Landing / Clubs / ClubDetail / Bars / BarDetail / Submit / Profile / Favorites
- 服务层：clubsService / barsService / reviewsService / favoritesService / vibeService
- 认证：已引入 AuthContext（全局 session），但仍需系统性审计

1.2 风险观察
- 测试目录缺失：当前未发现 test/spec 文件
- CI 缺失：未发现 .github/workflows
- 体验一致性风险：
  - `vibeService` 仍依赖本地样本数据，线上一致性不足
  - 部分业务提示文案、异常处理风格不统一
- 代码质量风险：
  - 服务层直接处理较多转换逻辑，边界条件依赖人工维护
  - 收藏、评论、鉴权多个页面仍存在重复“判断+提示”模式

1.3 成熟化目标定义
一个成熟版本（MVP+）必须满足：
- 稳定性：P0 崩溃 bug 归零；关键路径可回归
- 质量：PR 必须通过 lint + typecheck + tests
- 安全：Auth/RLS 规则可审计；敏感配置可控
- 可运维：错误可追踪，性能可观测，可快速回滚
- 可增长：有埋点、有漏斗、有迭代节奏

-------------------------------------------------------------------------------
2. 成熟化总路线（阶段化）
-------------------------------------------------------------------------------
Phase 0：基线冻结与审计（1 周）
Phase 1：工程质量基建（1~2 周）
Phase 2：认证与权限体系固化（1 周）
Phase 3：数据与 Supabase 迁移规范化（1 周）
Phase 4：核心功能稳定性修复（2 周）
Phase 5：测试体系（2 周）
Phase 6：性能与体验优化（1~2 周）
Phase 7：安全与合规（1 周）
Phase 8：发布与运营体系（1 周）

4. 执行纪律（确保“万无一失”）
-------------------------------------------------------------------------------
每个阶段都执行以下 8 条硬规则：
1) 先写变更计划，再改代码
2) 一次只做一个主题，不跨阶段混改
3) 每次提交都包含“可回滚说明”
4) 改动后必须跑：lint + typecheck + build + 相关测试
5) 所有异常路径都要有用户可理解提示
6) 所有数据库变更都要有 migration 与回退思路
7) 文档与代码同提交（文档不同步视为未完成）
8) 每周做一次风险复盘与优先级重排
