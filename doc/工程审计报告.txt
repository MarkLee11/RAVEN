一、总体结论
-------------------------------------------------------------------------------
项目处于“功能可用、工程化不足”的阶段。

优势：
1) 核心业务闭环已具备：浏览 -> 详情 -> 评论 -> 收藏 -> 个人页
2) 已采用 TypeScript + Supabase + RLS，技术方向正确
3) 已有部署配置（Netlify + Vercel rewrite）
4) 近期已补全全局 AuthContext，会话一致性明显改善

短板：
1) 自动化测试体系缺失（无单测、无 E2E）
2) CI/CD 缺失（无 GitHub Actions 工作流）
3) 数据/迁移治理流程不统一（大量 SQL 与 scripts 并存）
4) 可观测性缺失（无错误追踪、性能指标、业务埋点）
5) 服务层存在潜在性能点（N+1 查询、重复请求）

成熟度评估（1-5）：
- 架构清晰度：3
- 功能完整度：3
- 代码质量：3
- 测试能力：1
- 发布能力：2
- 可运维能力：1
- 安全治理：2
综合：2.1/5

二、分域审计结果
-------------------------------------------------------------------------------
2.1 前端架构与状态管理
- 现状：
  - 页面路由集中在 `src/App.tsx`
  - 业务逻辑已下沉到 `src/services/*`
  - `src/contexts/AuthContext.tsx` 已建立全局登录态
- 风险：
  - 受保护路由仍是“页面内判断”为主，建议升级为统一 Guard
  - `SubmitReview` 强依赖 `location.state` 传参，直接访问 `/submit` 会降级到提示页

2.2 认证与会话
- 现状：
  - `supabase.ts` 已开启 `persistSession/autoRefreshToken`
  - Profile 已使用 `data.session` 区分“已登录”和“仅注册成功待验证”
- 风险：
  - 收藏服务仍直接多处 `getUser()`，会造成重复鉴权请求
  - 登录、注册、重定向路径策略尚未沉淀成统一规范文档

2.3 数据访问与服务层
- 现状：
  - `clubsService` / `barsService` 支持筛选与聚合评分
  - `reviewsService` 支持 club/bar 双体系评论写入
- 风险：
  - `reviewsService.getUserReviewHistory` 存在 N+1 查询（每条 review 再查一次 venue）
  - 目前错误处理以 `console.error` 为主，缺乏用户级错误语义映射

2.4 数据库与迁移
- 现状：
  - 存在 `sql/` 与 `supabase/migrations/` 两套 SQL 来源
  - Favorites 已有独立 `bar_favorites/club_favorites` 表结构脚本
- 风险：
  - 迁移命名、执行顺序、环境隔离未形成硬规范
  - mock/simple/real 数据大量并存，容易误用到生产流程

2.5 测试与质量门禁
- 现状：
  - `package.json` 当前仅有 `dev/build/lint/preview`
  - 未发现 test/spec 文件
- 风险：
  - 缺乏回归防线，改动后只能人工验证
  - 无覆盖率，无法衡量质量基线

2.6 CI/CD 与发布
- 现状：
  - 有 `netlify.toml`、`vercel.json`，可部署
  - 未发现 `.github/workflows/*.yml`
- 风险：
  - PR 不受自动化检查约束
  - 无标准化发布清单与回滚演练

2.7 可观测性与运维
- 现状：
  - 暂无明显接入 Sentry/Datadog/GA 代码
- 风险：
  - 线上问题定位成本高
  - 无法评估漏斗转化和性能波动
