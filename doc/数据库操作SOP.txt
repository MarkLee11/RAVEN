===============================================================================
RAVEN 数据库操作 SOP（Phase 3）
===============================================================================
日期：2026-09-20
适用：Supabase + 本地 SQL 数据导入流程

-------------------------------------------------------------------------------
1. 环境分层（必须）
-------------------------------------------------------------------------------
1) dev：本地开发/功能联调
2) staging：上线前验证
3) prod：生产

规则：
- 禁止将 `sql/mock-data`、`sql/simple-data` 直接导入 prod
- prod 仅允许通过已审核 migration + 受控 SQL 执行

-------------------------------------------------------------------------------
2. 目录职责边界
-------------------------------------------------------------------------------
- `supabase/migrations/*.sql`
  - 只放结构性变更、策略变更、受控数据修正
  - 可追溯、可审计、可按序执行

- `sql/*.sql`
  - 研发辅助脚本、批量导入、分析脚本
  - 默认不作为“生产迁移真源”

建议：
- 未来将“真正要上生产的 SQL”统一迁入 `supabase/migrations`

-------------------------------------------------------------------------------
3. 迁移命名规范
-------------------------------------------------------------------------------
推荐格式：
`YYYYMMDD_HHMM_<scope>_<action>.sql`

示例：
- `20260920_0830_auth_add_require_auth_policies.sql`
- `20260920_0910_reviews_add_index_for_user_created_at.sql`

-------------------------------------------------------------------------------
4. 迁移执行流程（标准）
-------------------------------------------------------------------------------
Step 1：准备
- 新建 feature 分支
- 明确变更范围（表/索引/策略/函数）

Step 2：编写迁移
- 一个迁移只做一个主题
- 所有 `DROP` 操作要谨慎，优先 `IF EXISTS`

Step 3：评审
- 评审 SQL 风险：锁表、数据量、回滚难度

Step 4：staging 验证
- 执行迁移
- 跑关键业务回归（登录、评论、收藏、列表查询）

Step 5：prod 执行
- 在低峰时段发布
- 发布后监控错误与查询延迟

-------------------------------------------------------------------------------
5. 回滚策略
-------------------------------------------------------------------------------
1) 所有迁移提交时必须附“回滚思路”
2) 原则上用“反向迁移”回滚，不建议 destructive reset
3) 涉及数据删除的迁移必须先备份

-------------------------------------------------------------------------------
6. 数据导入策略
-------------------------------------------------------------------------------
mock/simple/real 的使用边界：
- `sql/mock-data`：仅 dev 演示、压测模拟
- `sql/simple-data`：轻量样例验证
- `sql/real-data`：仅在 staging 验证后，按批次受控导入

导入前检查：
- 外键依赖是否满足（districts/themes/bars/clubs）
- RLS 与角色权限是否匹配
- 唯一约束冲突预检查

-------------------------------------------------------------------------------
7. 与 CI/CD 对接建议
-------------------------------------------------------------------------------
短期：
- 在 PR 模板中加入“DB 变更检查项”

中期：
- 增加 migration lint/check job
- 增加 staging smoke SQL 验证

-------------------------------------------------------------------------------
8. 禁止事项
-------------------------------------------------------------------------------
- 直接在 prod 手工执行未评审 SQL
- 把 mock 数据脚本当作迁移执行
- 无回滚说明的高风险变更
